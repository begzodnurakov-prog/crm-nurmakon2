# Crm_nurmakon

Flask/SQLAlchemy learning-center CRM with role-based accounts, student and group management, class-session attendance, and payment tracking.

## Project structure

```text
app.py                  App factory, routes, access rules, and CLI commands
config.py               Environment-driven session, database, and rate-limit settings
extensions.py           Shared SQLAlchemy, Login, CSRF, Migration, and Limiter extensions
models.py               User, Student, Group, ClassSession, Attendance, Payment, Notification, and Inquiry models
schema_bootstrap.py     One-time, idempotent migration from the original SQLite prototype
migrations/             Alembic environment and versioned schema revisions
static/                 PWA manifest, icons, offline page, and service worker
templates/              Bootstrap 5 pages organized by workflow
tests/                  In-memory route and legacy migration regression tests
requirements.txt        Runtime dependencies
render.yaml             Render web, PostgreSQL, and Redis-compatible service blueprint
Procfile                Gunicorn start command for Procfile-based hosts
.gitignore              Excludes local environments, secrets, and database files
instance/               Local SQLite database and pre-upgrade backup; excluded from source control
```

## Local setup (PowerShell)

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Before migrating an existing database, stop the development server and make a backup:

```powershell
Copy-Item .\instance\nurmakon.db .\instance\nurmakon.before-crm-upgrade.db
```

For the existing prototype database, run the one-time compatibility upgrade. It preserves student/payment rows, retains the old daily attendance table as `legacy_attendance`, and maps those records to class sessions. Then record the current schema as the Alembic baseline:

```powershell
python -m flask --app app init-db
python -m flask --app app db stamp head
python -m flask --app app create-admin
python -m flask --app app run --debug
```

For a brand-new empty database, use the versioned schema instead of the legacy bootstrap:

```powershell
python -m flask --app app db upgrade
python -m flask --app app create-admin
```

The first administrator is created through a hidden password prompt. Public self-registration is disabled; only an administrator can create accounts from **Foydalanuvchilar**. Admins assign teacher and parent/student roles, provision additional administrator accounts, assign teachers to groups, and link parent accounts to students.

Run tests with:

```powershell
python -m unittest discover -s tests -v
```

## Notifications and support

Attendance changes create an in-app notification for linked parent accounts. Tuition and upcoming-class reminders are queued idempotently by the CLI command below; schedule it to run daily using Windows Task Scheduler or a production scheduler. Running it repeatedly does not duplicate a reminder for the same payment due date or class session:

```powershell
python -m flask --app app send-reminders --days 3
```

These notifications are stored in the CRM and shown in the dashboard/notification center; this implementation does not send email or SMS. Parents can submit an inquiry under **Aloqa / yordam** and see replies there. Administrators review, respond to, and resolve requests under **Murojaatlar**. Link parent accounts to students in the student editor to enable student-specific alerts.

## Courses and groups

Administrators manage course titles, monthly prices, and durations under **Kurslar**, then create groups with an assigned course, teacher, room, meeting-day pattern, and start time under **Guruhlar**. A student can be enrolled in multiple groups from each group's detail page; existing single-group assignments are migrated as enrollments and remain the student's primary group for compatibility. Teachers and administrators open daily attendance from the teacher portal or group detail, select a date, and save the roster in one batch. Monthly rates include session and daily marks, treat late as attended, exclude excused records, and prefer a daily mark when the same student has a session mark on that date. Apply the new schema revisions to an existing CRM with `python -m flask --app app db upgrade` after backing up the database.

## Schema changes after bootstrap

For future model changes, generate and review a migration, then commit the generated script:

```powershell
python -m flask --app app db migrate -m "describe schema change"
python -m flask --app app db upgrade
```

Review autogenerated migrations before applying them to production. Back up the database and test upgrades against a copy first.

## Production configuration

Set these environment variables in the hosting platform, not in source control:

- `APP_ENV=production`
- `SECRET_KEY`: long, randomly generated secret shared across application instances
- `DATABASE_URL`: managed PostgreSQL URL; SQLite is intentionally rejected in production
- `RATELIMIT_STORAGE_URI`: shared Redis URL for rate limits across workers
- `SESSION_COOKIE_SECURE=true` when HTTPS is enabled

Install a PostgreSQL driver such as `psycopg[binary]` in the deployment image for PostgreSQL URLs. Run migrations as a release step, serve the app with a production WSGI server (Waitress is included for Windows), configure HTTPS at the proxy, and schedule encrypted backups. The built-in rate limiter defaults to in-memory storage for local development only.

Example Windows production server command after environment configuration:

```powershell
waitress-serve --listen=127.0.0.1:8000 app:app
```

## Installable PWA

The manifest is served at `/static/manifest.json`; `/service-worker.js` is deliberately exposed at the site root so it can control `/`. The worker caches only the public PWA shell and icons. It does not cache authenticated dashboard pages or form submissions; offline navigation displays a generic offline page instead. Install prompts require HTTPS in production (localhost is allowed for development). iOS users can use Safari's **Add to Home Screen** action.

## Deploy to Render

The repository includes a Render Blueprint (`render.yaml`) that creates a Python web service, PostgreSQL database, and Redis-compatible Key Value service. `Procfile` contains the equivalent Gunicorn command for other Procfile-based hosts.

1. Push this project to a GitHub repository. Do not commit `.env`, `instance/nurmakon.db`, or database backups; `.gitignore` already excludes them.
2. In Render, choose **New > Blueprint**, connect the repository, and apply `render.yaml`. Select the same region for all three services. Render will request approval before creating them.
3. Wait for the web service to deploy. The configured start command runs `flask db upgrade` before starting Gunicorn. Check the deploy logs and visit the generated `onrender.com` URL.
4. Create the first admin. For a paid Render web service, open its Shell and run `python -m flask --app app create-admin`. On a Free web service (no Shell access), run the command locally with `DATABASE_URL` set to the database's **external** URL; temporarily allow your current IP in the database's IP allowlist, then remove that IP after the admin has been created. The command prompts for the password without echoing it.

Example local PowerShell session for the admin bootstrap:

```powershell
$env:APP_ENV = "development"
$env:DATABASE_URL = "<Render PostgreSQL external URL>"
python -m flask --app app create-admin
Remove-Item Env:DATABASE_URL
Remove-Item Env:APP_ENV
```

The app normalizes Render's `postgresql://` URL for psycopg 3. Do not set `APP_ENV=production` for this local admin command; the app would also require a strong `SECRET_KEY` and a Redis URL. The deployed service receives those from Render.

### SQLite and persistence

Do **not** deploy `instance/nurmakon.db` as the live database on Render. A Render web service's filesystem is ephemeral, so that file can disappear on restart, redeploy, or free-service spin-down. This app also intentionally rejects SQLite when `APP_ENV=production`; the Blueprint uses PostgreSQL and shared Redis instead.

The first `flask db upgrade` creates the schema only. It does **not** copy rows from your local SQLite database. Keep a verified backup of `instance/nurmakon.db`. If its existing student, payment, user, or attendance data must go live, migrate a copy into PostgreSQL with a deliberate SQLite-to-Postgres data-transfer process, validate row counts and relationships, and only then switch users to the cloud URL. Do not point a deployed app at your local SQLite path or assume Git uploads that ignored file.

Render's Free web service sleeps after inactivity. Its Free PostgreSQL database is limited to 1 GB, has no backups, and expires 30 days after creation (with a 14-day upgrade grace period before deletion). Free Key Value data is not persistent, so rate-limit counters can reset. Treat the Free Blueprint as a demo; upgrade PostgreSQL and Key Value to paid plans and configure backups before storing real learner or payment records. Free web services cannot attach persistent disks; a paid single-instance Render service with a persistent disk can support SQLite only if you deliberately change the app's production configuration and set `DATABASE_URL=sqlite:////data/nurmakon.db`, but PostgreSQL remains the recommended option.

For production at multiple web instances, move `flask db upgrade` out of `startCommand` and into Render's paid **Pre-Deploy Command** (`python -m flask --app app db upgrade`). Running migrations on each instance startup is appropriate only for the single-instance demo Blueprint.
